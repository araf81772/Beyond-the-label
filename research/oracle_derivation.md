# Analytic oracle derivation

This is an AI-derived algebraic reference, independently checked against the literal values in design Section 4. It is not empirical evidence, human verification, or a claim that H1 has occurred. `evaluation/oracle_table.csv` is generated by the oracle module and is research-only. Only NUMERIC's expressly prescribed three first-action losses may appear in requests.

Let `q_i` be the accuracy of archived report i, `P_i` its wrong-disposition penalty, and `f` the inspection fee. For known scope, `q_IN = 9/10` and `q_OOS = 3/5`. RELEASE follows a PASS report; HOLD follows a FAIL report. Because each accuracy exceeds one-half, following an unchecked report minimises its expected penalty.

- Commit following both reports: `(1-q_1)P_1 + (1-q_2)P_2`.
- Inspect lot 1, then act optimally: `f + (1-q_2)P_2`.
- Inspect lot 2, then act optimally: `f + (1-q_1)P_1`.
- Against-report disposition on an unchecked lot: `q_i P_i`, not `(1-q_i)P_i`.
- After inspection, its state is exact: a correct disposition costs zero penalty; a wrong one costs `P_i`. The inspection fee is included exactly once.

| Condition / assignment | Commit following reports | Inspect first named lot | Inspect other |
|---|---:|---:|---:|
| MAIN, lot_1 OOS | 40 + 10 = 50 | 20 + 10 = 30 | 20 + 40 = 60 |
| MAIN, lot_1 IN | 10 + 40 = 50 | 20 + 40 = 60 | 20 + 10 = 30 |
| HIGH-FEE, lot_1 OOS | 40 + 10 = 50 | 60 + 10 = 70 | 60 + 40 = 100 |
| HIGH-FEE, lot_1 IN | 10 + 40 = 50 | 60 + 40 = 100 | 60 + 10 = 70 |
| HIGH-STAKES, H OOS | 320 + 10 = 330 | 20 + 10 = 30 | 20 + 320 = 340 |
| HIGH-STAKES, H IN | 80 + 40 = 120 | 20 + 40 = 60 | 20 + 80 = 100 |
| MASKED, identity unknown | 25 + 25 = 50 | 20 + 25 = 45 | 20 + 25 = 45 |

NUMERIC uses the same 50/30/60 or 50/60/30 values as MAIN. The user's pre-freeze amendment retains report facts alongside these supplied losses; it changes no numerical oracle value.

In MAIN the oracle loss is 30, always committing while following reports costs 50, and a uniformly random single inspection costs `(30+60)/2 = 45`. These are reference-policy expectations, not measured performance.

## MASKED continuation

MASKED supplies exactly-one-IN information but no identity. Before inspection each target's marginal report accuracy is `(.9+.6)/2 = .75`, yielding the hand-table row above. An inspection also conveys information about the shared unknown scope assignment. This does not imply dependence of states conditional on the actual scope assignment.

If the inspected state matches its report, the posterior probability that the inspected report is IN is `.9/(.9+.6) = .6`. The other report's accuracy is therefore `.6*.6 + .4*.9 = .72`. Its expected wrong-disposition cost following the report is 28 at penalty 100; total loss conditional on this observation is `20+28 = 48`.

If inspection contradicts the report, the corresponding posterior is `.1/(.1+.4) = .2`. The other report's accuracy is `.2*.6 + .8*.9 = .84`; total expected loss is `20+16 = 36`. Both .72 and .84 exceed .5, so the optimal continuation still follows the unchecked report. Averaging over the inspection yields `.75*48 + .25*36 = 45`, exactly the pre-inspection table value. These posterior expectations use only visible reports and the legitimate inspected state, never hidden scope identity or the uninspected hidden state.

## Invalid-action sensitivity

The design scores exact valid commit dispositions, so the valid first-action space includes all four RELEASE/HOLD combinations. `worst_valid_loss` takes the maximum over those commits and the two inspection actions valued with optimal continuation. For MAIN, the valid commit against both reports costs `.6*100 + .9*100 = 150`; using only the table's maximum of 60 would omit a valid action. Thus an invalid MAIN first action receives sensitivity regret `150-30 = 120`, while its valid-only regret remains missing. This interpretation is recorded for pre-freeze review; it does not change valid-action scoring or the hand table.

## Reproduce

From the repository root in PowerShell, with project `src` available on Python's module path:

```powershell
$env:PYTHONPATH = 'src'
python -m beyond_label.oracle --output evaluation/oracle_table.csv
python -m pytest tests/test_oracle_matches_hand_table.py -q
```

The implementation uses `fractions.Fraction` internally and converts only returned API values to floats. The tests contain literal Section 4 values independently of the generated CSV, enumerate all immediate commit arguments, and exercise both inspection outcomes. The generated reference CSV must never be treated as observed scores or sent wholesale to a model.
